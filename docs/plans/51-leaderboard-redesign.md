# Leaderboard Redesign — GH Issue #51

## Context

Issue #51 promotes the league leaderboard from a 2-column rank/team table into the league hub: position, team, owner, position-change, and cumulative season points, with a richer header. The scoring engine (#17) is already done — `TeamRaceWeekendScore` rows exist per (team, race weekend) — but nothing aggregates them into season totals or exposes them as standings. The current `Leaderboard.tsx` renders only rank + team name + owner + a "View" button against the unsorted `LeagueDetailsResponse.Teams` array.

This plan implements the design at `docs/mockups/design_handoff_leaderboard_redesign/`. Decisions reflect explicit user answers in the planning conversation:

- Header chips: ship `Round X / Y` and `After {Race} {Session}` only. The `Next ...` chip is dropped (no session-start-time data exists; out of scope).
- `positionChange`: computed from a persisted `LeagueStandings` table. Standings rows are written by the scoring orchestrator (`ScoringService.ScoreRaceWeekendAsync` calls `LeagueStandingsService.UpdateStandingsForRaceWeekendAsync(raceWeekendId)`) after each weekend is scored; the read-side computes the delta as `priorRound.position - currentRound.position`. Reasoning: standings are read-heavy and write-rarely (tens of writes vs. potentially thousands of reads per league per season), and a future "team finishing positions across the season" view is shaped exactly like the persisted table. Recomputing on every read is the wrong asymmetry for this data.
- Standings live on a new `GET /leagues/{id}/standings` endpoint (separate from `GET /leagues/{id}`).
- Tie-break: `totalPoints DESC, teamId ASC`. Formal end-of-season tie-breakers (weekend wins, highest single round) are deferred to a future season-finale change — they don't surface in the leaderboard UI mid-season and only matter if a tie at #1 actually exists at season end. Building them now would be YAGNI; leaving them out simplifies the entity (two columns instead of four) and the writer (no per-round unique-winner detection).
- Session label uses **"Grand Prix"** (not "Race") even when redundant with `RaceWeekend.Name`.
- Single-DOM responsive layout: one `<ul>` of `<li>` rows using CSS Grid at every breakpoint, with `grid-template-columns` and per-cell visibility swapping at `sm` (640px). The handoff describes two layouts (table on desktop, cards on mobile), but they share enough structure that recreating them as a single tree with responsive utilities matches the visual spec without rendering rows twice. Trades modest markup density for simpler tests, no drift risk between layouts, and proper list semantics. The Move column's position swap (its own grid cell on desktop vs. inline within the team block on mobile) is handled by rendering `<PositionDelta>` in two grid positions, with `hidden sm:block` / `sm:hidden` on each — only that one element is dual-rendered, not the whole row.
- Direct replacement of the existing `Leaderboard.tsx` — no flag, no V2-side-by-side.
- "Current race weekend" is **scoring-driven**, not calendar-driven. `RaceWeekendService.GetCurrentSeasonRaceWeekendAsync()` (no param) returns the earliest weekend in the current season whose `ScoredAt IS NULL`. Lives on `RaceWeekendService` because it's the noun that owns "race weekend" — `RaceWeekendService` injects `ISeasonService` and resolves the current season internally so consumers (`TeamService`, `LeagueStandingsService`) don't have to compose two service calls each. Rationale lives in "Second design review" below.
- `GetLeagueStandingsAsync` (the response-DTO assembler for `GET /leagues/{id}/standings`) lives on `ILeagueStandingsService`, **not** `ILeagueService`. Rationale: the method's body is overwhelmingly standings-shaped, and placing it on `LeagueService` forces three new dependencies the rest of `LeagueService` doesn't need. See "Second design review" below.

## Data shapes

### `GET /api/leagues/{id}/standings`

```json
{
  "leagueId": 12,
  "round": 7,
  "totalRounds": 24,
  "afterRaceName": "Miami GP",
  "afterSessionType": 2,
  "standings": [
    {
      "teamId": 91,
      "teamName": "Mango Lassi Racing",
      "ownerId": 5,
      "ownerName": "Priya Iyer",
      "position": 1,
      "totalPoints": 1284,
      "positionChange": 0
    }
  ]
}
```

Field rules:

- `round` = the round of the race weekend that the API considers "current" — i.e., the first weekend in the current season whose `ScoredAt IS NULL`, ordered by `Round`. After the redefinition in commit 2.5, this is **scoring-driven**, not calendar-driven: `round` does not advance the moment `RaceDate` passes; it advances when `/score` runs and the weekend's `ScoredAt` is set. `null` only when every weekend in the season has been scored (season finale).
- `totalRounds` = `COUNT(RaceWeekend WHERE SeasonId = league's current season)`.
- Define `latestScoredRound` (internal, not in the response) = the highest `RaceWeekend.Round` for which a `LeagueStanding` row exists for this league. `null` if no standings rows have been written yet for this league. This anchors both `afterRaceName`/`afterSessionType` and `positionChange` below. Note this is per-league: a league created mid-season with no historical standings reads `null` here even when other leagues have rows for prior rounds.
- `afterRaceName` = the `Name` of the race weekend at `latestScoredRound`. Under the scoring-driven `round` definition, `round` and `latestScoredRound` are always adjacent (`latestScoredRound = round - 1` for active seasons; `latestScoredRound = totalRounds` for season-over) at the system level. They can still diverge **per-league** when a league has no standings rows for the latest scored weekend (newly created league, or zero teams with scoring activity); in that case `afterRaceName` is `null`. `null` if `latestScoredRound` is `null`.
- `afterSessionType` = the latest `SessionType` (in chronological order via `WeekendSessions.InOrder`) for the weekend at `latestScoredRound` that has a result row. For each session in the weekend's order, `EXISTS`-check the appropriate result table:
  - `SessionType.Sprint` → `EXISTS DriverRacingResult WHERE RaceWeekendId = X AND SessionType = Sprint`
  - `SessionType.Qualifying` → `EXISTS DriverQualifyingResult WHERE RaceWeekendId = X` (note: this enum value never appears in `DriverRacingResult`; qualifying lives in its own table)
  - `SessionType.GrandPrix` → `EXISTS DriverRacingResult WHERE RaceWeekendId = X AND SessionType = GrandPrix`
  - Pick the latest one in the weekend's chronological order that has rows. `null` if `latestScoredRound` is `null`. The user-facing label transform (`GrandPrix` → "Grand Prix") happens on the frontend.
- `positionChange = priorStanding.Position - currentStanding.Position`, where both rows come from `LeagueStandings` (current = `RaceWeekend.Round == latestScoredRound`, prior = `RaceWeekend.Round == latestScoredRound - 1`). `null` when `latestScoredRound` is `null`, when `latestScoredRound == 1`, or when no `LeagueStanding` row exists for that team at the prior round (e.g., team joined the league after the prior round was scored — there's no prior position to diff against).
- `standings` ordering — established by the writer at `UpdateStandingsForRaceWeekendAsync` time and persisted as `Position`. Sort key:
  1. `totalPoints` DESC (cumulative sum of `TeamRaceWeekendScore.TotalPoints` for this team across the season, computed incrementally from the prior round's `LeagueStanding` row plus this round's `TeamRaceWeekendScore`)
  2. `teamId` ASC — final deterministic tiebreak
- Standings rows are written forward only by the writer. A team that has scored at least once in the league has a `LeagueStanding` row carried forward at every subsequent scored round (the writer's incremental algorithm picks up their prior cumulative even when they didn't score this round). A team that has never scored in the league has no `LeagueStanding` row at any round, and the same is true for a team that joined the league after the most recent scoring run.
- The response always includes every team currently in the league. Teams with a `LeagueStanding` row at `latestScoredRound` show that row's `Position` and `TotalPoints`. Teams in the league without a row (never scored, or joined post-scoring) appear at the bottom of the standings with `TotalPoints = 0`, `positionChange = null`, and `Position` continuing from the last scored team's position, ordered among themselves by `TeamId` ASC. The zero-fill is the **reader's** responsibility — the writer only emits rows for teams with scoring activity, and the reader merges in current league membership at read time.
- When the league has zero `LeagueStanding` rows entirely (preseason or never-scored), the reader zero-fills every team in the league with `Position` 1..N ordered by `TeamId` ASC, both `after*` fields `null`. This is the degenerate case of the rule above (zero scored teams + N zero-filled teams).

### Session ordering (`WeekendSessions` helper)

The chronological order of sessions in an F1 weekend is not encoded anywhere in the codebase today (`SessionType` distinguishes racing-result rows; `WeekendFormat` only signals presence/absence of a sprint). To avoid sprinkling that knowledge across the standings query (and any future feature that needs it), do two small things:

**1. Extend the existing `SessionType` enum** with `Qualifying = 2`. The enum is already named generally; the fact that it's currently only used on `DriverRacingResult` is incidental, not definitional. Adding the value is source-only — no migration, since the column stores int and existing rows are unaffected.

```csharp
// api/F1CompanionApi/Data/Entities/SessionType.cs
public enum SessionType
{
    GrandPrix = 0,
    Sprint = 1,
    Qualifying = 2,
}
```

**2. Add a small static helper** that owns the chronological order:

```csharp
// api/F1CompanionApi/Domain/Models/WeekendSessions.cs

public static class WeekendSessions
{
    /// <summary>
    /// Sessions that occur in the given weekend format, in F1 chronological order.
    /// Standard weekends: Qualifying -> Grand Prix.
    /// Sprint weekends:   Sprint -> Qualifying -> Grand Prix.
    /// </summary>
    public static IReadOnlyList<SessionType> InOrder(WeekendFormat format) =>
        format switch
        {
            WeekendFormat.Sprint   => new[] { SessionType.Sprint, SessionType.Qualifying, SessionType.GrandPrix },
            WeekendFormat.Standard => new[] { SessionType.Qualifying, SessionType.GrandPrix },
            _ => throw new ArgumentOutOfRangeException(nameof(format)),
        };
}
```

User-facing labels are deliberately not here — the response ships `SessionType` directly and the frontend owns presentation (`GrandPrix` → "Grand Prix"). This helper is the seam that a future "Session entity" refactor (see `docs/plans/draft-issue-session-entity.md`) would replace. Keeping the chronological-order knowledge in one place now means that swap is a one-file change later.

### `LeagueStandings` contract (frontend)

```ts
// web/src/contracts/LeagueStandings.ts
export interface StandingsEntry {
  teamId: number;
  teamName: string;
  ownerId: number;
  ownerName: string;
  position: number;
  totalPoints: number;
  positionChange: number | null;
}

// Numeric enum to match the backend's wire format (no JsonStringEnumConverter
// is registered; existing `WeekendFormat` ships the same way).
export enum SessionType {
  GrandPrix = 0,
  Sprint = 1,
  Qualifying = 2,
}

export interface LeagueStandings {
  leagueId: number;
  round: number | null;
  totalRounds: number;
  afterRaceName: string | null;
  afterSessionType: SessionType | null;
  standings: StandingsEntry[];
}

// Display transform — backend ships the canonical enum, frontend renders.
// `null` for GrandPrix is intentional: race names like "Miami Grand Prix"
// already encode the session, so re-appending "Grand Prix" reads as redundant
// ("After Miami Grand Prix Grand Prix"). When this returns null, the consumer
// (e.g. the leaderboard "After" chip) should omit the session segment entirely.
// Sprint and Qualifying always render — those carry information the race name
// doesn't, and signal that scoring is mid-weekend.
export const sessionTypeLabel: Record<SessionType, string | null> = {
  [SessionType.Sprint]: 'Sprint',
  [SessionType.Qualifying]: 'Qualifying',
  [SessionType.GrandPrix]: null,
};
```

## Architectural pivot (historical note)

This plan was originally written for an on-the-fly standings computation. After a design review the architecture pivoted to persisted standings (rationale captured in the decisions list above). The pivot's plan-doc edits landed in `dfd5f96` (`docs(leaderboard): refine #51 plan with review findings`); the on-the-fly stub of `LeagueService.GetLeagueStandingsAsync` and its endpoint registration were reverted to `main` so commit 2 could land cleanly. Files that were kept across the pivot (DTOs, `WeekendSessions` helper, `SessionType.Qualifying`, the `RaceWeekendService` "current weekend" method) stay uncommitted through commit 2 and land in commit 3.

## Second design review (mid-implementation)

Two follow-up decisions came out of a review while commit 3 was in flight:

1. **`GetLeagueStandingsAsync` lives on `LeagueStandingsService`, not `LeagueService`.** Originally the plan put it on `LeagueService` next to `GetLeagueByIdAsync`. The reviewer flagged that the method's body is overwhelmingly standings-shaped (latest-row lookup, prior-round diff, session-with-results probes against result tables) and that putting it there forced `LeagueService` to take three new dependencies (`ISeasonService`, `IRaceWeekendService`, `ILeagueStandingsService`) it otherwise wouldn't need. Moving it onto `LeagueStandingsService` keeps `LeagueService`'s constructor at its original 2 args and keeps the standings reader colocated with the writer + low-level read helpers. The endpoint at `LeagueEndpoints.GetLeagueStandingsAsync` injects `ILeagueStandingsService` directly. URL grouping (`/leagues/{id}/standings` is still a sub-resource of `/leagues`) is independent of service ownership — `LeagueEndpoints` already routes through `ILeagueInviteService` for invite-related endpoints, so multi-service dispatch from one endpoint file is a precedent.

2. **"Current race weekend" becomes scoring-driven (commit 2.5).** Originally the "current weekend" lookup was calendar-based (`RaceDate >= now`), which advances the moment a race finishes. That creates a transient inconsistency between race-end and scoring-end: the team page header would advance to "Round 2 · Saudi GP" while the leaderboard for that league still shows zero standings (because scoring hasn't run for round 1 yet). The fix is to redefine "current weekend" as the earliest weekend whose `ScoredAt IS NULL` — calendar-independent, advances only when `/score` writes the marker. This unifies the team page and leaderboard views: both treat the just-finished weekend as "still current" until scoring catches up. Lineup integrity through scoring is preserved by virtue of `LockDeadline` being in the past for the still-current weekend (existing `RosterLockedException` gate continues to work). Lineup edits *for the next weekend* are blocked through the post-race-pre-score window — intentional, since the user (admin) is the one running scoring and the gap is expected to be short. Frontend lock UI requires no change: the per-second tick on `Team.tsx` already derives `isLocked` from the shipped `lockDeadline`, which (under the redefinition) is the just-finished weekend's already-past `lockDeadline` during the post-race-pre-score window — tick correctly resolves to locked.

These decisions land as commit 2.5 (the redefinition + consolidation), inserted between commits 2 and 3 so commit 3 is authored against the scoring-driven semantics from the start. Commit 2.5 owns the addition of `RaceWeekendService.GetCurrentSeasonRaceWeekendAsync` (no param, scoring-based body, internal current-season resolution) and the `CurrentRaceWeekendTests` integration coverage; commit 3 consumes the method via `IRaceWeekendService` injection. The standings reader's logic in commit 3 (the latest-LeagueStanding-row query in `LeagueStandingsService.GetLeagueStandingsAsync`) gives the right answer under either definition — it's per-league, not system-level — so its body is identical regardless of which "current weekend" definition the rest of the API uses.

3. **Add `StandingsRanker`** at `Domain/Services/StandingsRanker.cs` — pure-function static class, no DI:
   ```csharp
   public static class StandingsRanker
   {
       public static IEnumerable<LeagueStanding> Rank(
           int leagueId,
           int raceWeekendId,
           IReadOnlyList<TeamRaceWeekendScore> scoresInLeague,
           IReadOnlyDictionary<int, LeagueStanding> priorByTeam,
           DateTime calculatedAt);
   }
   ```
   For each team in `scoresInLeague`: `newTotalPoints = (priorByTeam.GetValueOrDefault(teamId)?.TotalPoints ?? 0) + thisRoundPoints`. Sort by `TotalPoints DESC, TeamId ASC`. Assign `Position = idx + 1`. Returns one `LeagueStanding` row per scoring team. Extracted from the service so the ranking math is unit-testable with no DB or DI setup.

4. **Add `LeagueStandingsService`** at `Domain/Services/LeagueStandingsService.cs`. Public surface:
   ```csharp
   public interface ILeagueStandingsService
   {
       Task UpdateStandingsForRaceWeekendAsync(int raceWeekendId);
       Task<IReadOnlyList<LeagueStanding>> GetStandingsAsync(int leagueId, int round);
       Task<IReadOnlyList<LeagueStanding>> GetPriorStandingsAsync(int leagueId, int round);
   }
   ```
   The writer takes a `raceWeekendId` (the orchestrator already has it) rather than `(seasonId, round)` — the service derives `SeasonId` and `Round - 1` internally to find the prior weekend.

   **Incremental algorithm.** Inside `UpdateStandingsForRaceWeekendAsync`, per the scored weekend:
   - Load the weekend (throw if missing); pull this-weekend team scores from `TeamRaceWeekendScore` (all teams in one query — no per-league filter; the writer fans out across leagues).
   - Resolve `priorWeekendId` from `RaceWeekends` where `SeasonId == weekend.SeasonId && Round == weekend.Round - 1`. Null for round 1.
   - Find the leagues affected: `LeagueTeams` where `TeamId IN (scoringTeamIds)`. Distinct `LeagueId` set.
   - Pull prior standings for those leagues at `priorWeekendId` (empty list when prior is null).
   - Pull the active `LeagueTeams` membership for those leagues so the ranker only sees teams currently in each league.
   - Per league via `SelectMany`: build `priorByTeam` dictionary, filter `thisRoundScores` to teams in this league, call `StandingsRanker.Rank(...)`. Concatenate into a single `newStandings` list.
   - Save: `ExecuteDeleteAsync` for `LeagueStanding` rows where `LeagueId IN (leagueIds) && RaceWeekendId == raceWeekendId`, then `AddRange` + `SaveChangesAsync` for `newStandings`. Wrap delete + insert in a single transaction so the upsert is atomic — and wrap the transaction in `_dbContext.Database.CreateExecutionStrategy().ExecuteAsync(...)`. The `ExecutionStrategy` wrap is required because Npgsql is configured with retries (`EnableRetryOnFailure`); a bare `BeginTransactionAsync` will throw at runtime when the strategy is enabled.

   **Late-join semantics**: standings are written forward only. A team joining at round 5 has no row in rounds 1–4's standings. They appear at round 5 onward; their `positionChange` at round 5 is `null` because no prior row exists. (In practice every team in a league earns a `TeamRaceWeekendScore` row for every weekend after they join, so there's no carry-forward case to handle — a team without a this-round score has never been in this league.)

   **Out-of-order rescore caveat**: rounds are assumed scored in order (matches F1 calendar). Rescoring round R after rounds > R have already been written would leave the later rounds stale. Out of scope for this commit; documented as a known limitation. A future `RecomputeFromWeekendAsync(raceWeekendId)` that walks forward can be added when retroactive scoring becomes a real workflow.

### Commit 2.5 — Backend: scoring-driven current race weekend

**Scope:** Replace the calendar-based "current race weekend" definition with a scoring-state-based one. Add `ScoredAt` column to `RaceWeekend`, set it inside `ScoreRaceWeekendAsync`, add `RaceWeekendService.GetCurrentSeasonRaceWeekendAsync()` (no param, scoring-state body, resolves the current season internally via `ISeasonService`), and consolidate `TeamService`'s private `GetCurrentRaceWeekendAsync` onto the new method. Lands between commit 2 (which adds the standings writer) and commit 3 (which builds the read endpoint), so commit 3 can rely on the scoring-driven semantics from the start.

**Rationale:** see "Second design review" above. The short version: today the team page header advances the moment a race finishes (calendar-driven), but the leaderboard for that league won't reflect the race until `/score` runs. Scoring-driven current keeps both views aligned through the post-race-pre-score window. Lineup edits stay blocked across that window via the existing `RosterLockedException` gate (LockDeadline is past for the still-current weekend). Frontend tick-based lock UI continues to work without change.

**Implementation:**

1. **Add `ScoredAt` field on `RaceWeekend`**
   - `api/F1CompanionApi/Data/Entities/RaceWeekend.cs` — add `public DateTime? ScoredAt { get; set; }` after `LockDeadline`.
   - Generate migration: `dotnet ef migrations add AddScoredAtToRaceWeekend --project F1CompanionApi`. Single nullable column, no FK, no index needed (queries always filter by `SeasonId` first; `(SeasonId, ScoredAt)` is a low-cardinality lookup that PG handles fine via the existing `SeasonId` access path).
   - **No backfill.** Existing dev/prod weekends will read as `ScoredAt = null` ("unscored") until `/score` runs against them. User has explicitly stated this is acceptable.

2. **Set `ScoredAt` at the end of `ScoreRaceWeekendAsync`** + **lift the weekend lookup into the orchestrator**
   - `api/F1CompanionApi/Domain/Services/ScoringService.cs` — change the substep signatures from `(int raceWeekendId)` to `(RaceWeekend weekend)` for both `ScoreRaceEntitiesAsync` and `ScoreTeamsForRaceAsync`. `ScoreRaceWeekendAsync(int)` does the single `FindAsync ?? throw` at the top, threads the entity through both substeps, then sets `weekend.ScoredAt = DateTime.UtcNow` on the same tracked entity and saves. `UpdateStandingsForRaceWeekendAsync` stays id-based — cross-service boundary.
   - **Why entity, not id:** every substep call is in-process, same `DbContext`, same scope — passing a reference avoids redundant `FindAsync` round-trips and makes the weekend's existence a type-system precondition instead of a runtime check duplicated across each substep. The id-form is reserved for boundaries that serialize (HTTP, queues, cross-service), which this isn't.
   - **Test impact:** existing entity-level tests (`ScoreRaceEntitiesAsync_*`, `ScoreTeamsForRaceAsync_*`) bind a `var race = SeedRace(...)` and pass it. `ScoreRaceEntitiesAsync_RaceNotFound_Throws` renames to `ScoreRaceWeekendAsync_RaceNotFound_Throws` since the throw moves to the orchestrator.
   - **Idempotency:** re-running `/score` overwrites `ScoredAt` with the latest timestamp ("most recent successful run wins"). If "first scored at" semantics ever become useful, that's a separate field.
   - **Failure semantics:** `ScoreRaceWeekendAsync` currently doesn't wrap its three substeps (`ScoreRaceEntitiesAsync`, `ScoreTeamsForRaceAsync`, `UpdateStandingsForRaceWeekendAsync`) in an outer transaction. Setting `ScoredAt` last means the marker reflects "all three substeps completed successfully without throwing" — a partial failure leaves `ScoredAt` null, which is the correct outcome (treat the weekend as unscored, retry by rerunning `/score`). Adding an outer transaction is a separate correctness improvement, out of scope for this commit.

     - Chip row, with each chip conditioned independently:
       - "Round" chip — render when `standings.round != null`: `Round {standings.round} / {standings.totalRounds}`
       - "After" chip — render when `standings.afterRaceName != null` (which implies `afterSessionType != null`). Format: ``After {standings.afterRaceName}`` plus, when `sessionTypeLabel[standings.afterSessionType] != null`, ` · {sessionTypeLabel[standings.afterSessionType]}`. So Sprint scored → "After Miami Grand Prix · Sprint"; Qualifying scored → "After Miami Grand Prix · Qualifying"; Grand Prix scored → "After Miami Grand Prix" (session label omitted because the race name already encodes it). The presence/absence of the session segment is itself a signal: if you see one, scoring is still mid-weekend.

After the season's final race, `round` is `null` (no upcoming weekend) but `afterRaceName` is still set — the user should still see "After Abu Dhabi Grand Prix" even though the "Round" chip is gone. Conversely, before the first scoring of a season, `round` is set but `afterRaceName` is `null`.
     - Chip row uses Tailwind `flex flex-wrap` on desktop and `-mx-4 overflow-x-auto px-4 pb-1 [scrollbar-width:none] [&::-webkit-scrollbar]:hidden` on `<sm`. No `Next` chip.
